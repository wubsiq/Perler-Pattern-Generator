## 豆师傅项目 · 熨烫预览（IronPreviewMixin）性能优化

### 背景
hh 反馈熨烫预览渲染约 10s，要求提速；效果待其发参考图后再调。

### 根因（实测，非推测）
在无头 Chromium 基准台逐层计时，定位到 `_buildIronGeometry` 单函数占 10 秒里的 **97%**（9103ms / 9345ms）。

真凶：**往 Path2D 逐条追加十几万条子路径，代价超线性**。250×250 稀疏图（约 20 万条子路径）9033ms；改成先攒 SVG path 字符串、最后 `new Path2D(d)` 一次 → 141ms。

越稀疏越糟：稀疏图里几乎每颗豆都是"边缘豆"，全部走 `_cellPath` 曲线分支，正好踩满最慢路径。
- solid（边缘豆 4%）: 251 → 47ms
- sparse（边缘豆 92%）: 9033 → 141ms
- checker（边缘豆 100%）: 同样量级

### 改动（mixins/IronPreviewMixin.js）
1. 新增 `_ironPathSink()` —— 鸭子类型路径累加器（moveTo/lineTo/quadraticCurveTo/closePath/rect），把两条路径攒成字符串，最后各建一次 Path2D。
2. **坐标必须保留 6 位小数**（`_ironR6` 逻辑内联在 sink 里）。3 位会在曲线端点差出 1~3 像素（maxDelta 255）。这是实测踩出来的，别降。
3. 纹理层 + 光照层合并为一次 `clip()`（原本各一次，clip 会强制同步等待光栅化）。

### 验证
- 几何逐像素回归：4 种图案（solid/photo/sparse/checker）× 3 尺寸 = 12 组，path 与 expandPath **全部零差异**
- 端到端：250×250 sparse 10205 → 408ms；热缓存 123ms
- 九种烫法 + 五档倍率全部冒烟通过
- 底板残影检查 PASS

## 第二轮：透明背景 + 澡巾烫纹理按参考图重做

### 需求
1. 熨烫预览背景要能选**透明**（导出 PNG 带 alpha）
2. 澡巾烫效果要贴近 hh 发的实拍参考图（"像老虎皮毛，密集脊线浮雕，明暗来自方向光"）

### 参考图量化（不是目测调的）
对参考图浅蓝面板做 FFT / PCA / 自相关，量到：
- 各向异性（梯度水平能量:垂直能量）**3.7 ~ 7.4**，均值 4.94
- 亮脊 PCA 长宽比 **4.4 ~ 5.3**，长 28px / 宽 5~6px
- 分布偏度 **-0.29**（参考图五样本跨度 -2.08~+1.72）
- 明暗标准差 **28.9 灰阶**
- 珠径 ≈ 14px，脊线间距 ≈ 4~8px（每颗豆 1.8~3.5 条脊）
- 光源：亮部质心偏移仅 2.8% 窗口 → 接近顶光偏前

### 关键发现：两条走错的路（都写进代码注释了）

**① 靠 fx:fy 格点密度比造方向性 —— 无效甚至反效果**
实测单层（oct=1）：
```
fx:fy = 1:1  → 各向异性 3.06
fx:fy = 4:22 → 各向异性 1.01   ← 比值越大越差
```
原因：sample() 沿 y 密采样只会让两轴梯度更平均，不是更 anisotropy。

**② 把 warp 压到极小来"保方向" —— 同样无效**
warp 不是破坏者，是**微调旋钮**：0.045 → 9.81，0.16 → 8.71，0.22 → 7.43。
它把方向性从高位往下拉，同时消掉过于规整的条纹感。

**真正控制方向性的是整数剪切 (a,s)**（采样坐标 a*u+s*v，脊线垂直于 (a,s)）：
```
(1,0) 0.0° → 1.25    (1,1) 45.0° → 1.19
(2,1) 26.6° → 6.90 ★  (3,1) 18.4° → 2.27
(4,1) 14.0° → 1.40    (1,2) 63.4° → 1.10
```
(2,1) 是甜点。

### 最终效果（三项主指标全部对齐）
| 指标 | 改前 | 改后 | 参考 |
|---|---|---|---|
| 各向异性 | 1.90 | **7.48** | 4.94 ✓ |
| 标准差 | 84.0 | **37.4** | 28.9 ✓ |
| 拉普拉斯 | 68.8 | **23.4** | 21.7 ✓ |
| 偏度 | -0.03 | -0.45 | -0.29（可接受，参考图自身跨度 ±2） |

平铺无缝：接缝比值 0.57~0.74（<1 表示接缝比内部还平）✓

### 透明背景实现
- 控件加「透明」按钮，预览用 CSS 棋盘格（不进位图），导出是真 alpha
- `drawIronPreview` 里 `clearRect` 替代填色
- **透明模式自动跳过投影**（否则一圈灰雾，很丑）
- state 加 `transparent` 字段，导出文件名带 `-alpha` 后缀
- 验证：alpha=0 区 82925px / alpha=255 区 1439982px / 半透明 4789px（边缘抗锯齿）✓

### 验证清单（全 PASS）
- 几何逐像素回归 9 组全一致（性能优化没被破坏）
- 性能未退化：250 sparse 2400ms（优化前 10205ms）
- 透明背景真透明、投影跳过、透明↔不透明来回切换零残影
- 九模式 × 透明/不透明 = 18 组冒烟全通过
- 导出 PNG 格式正确

### 遗留
- 偏度 -0.45 略低于参考 -0.29，可微调 gamma（实测 0.85 → -0.59 更接近）但影响观感有限
- 无头环境无 GPU，像素级视觉最终仍需 hh 真机确认

## 第三轮：熨烫预览「烟熏感 + 黑白没纹路」——找到算法级根因

### hh 的反馈（截图对比）
- 当前效果"像烟熏"
- **黑色和白色上面都没有纹路**
- 达不到写实效果

### ★ 根因：overlay 混合模式在数学上不可能做对

纹理 tile 以灰 128 为中性基准（`_newGrayTile` 的设计），用 `globalCompositeOperation='overlay'` 叠：

```
overlay: base<0.5 → 2·base·blend ；base≥0.5 → 1-2(1-base)(1-blend)
blend=0.5（灰128）时：
  base=0.00 → 0.0000   ← 原样不变
  base=1.00 → 1.0000   ← 原样不变
```

**任何"以中性灰为基准"的混合模式，在纯黑和纯白豆子上都是恒等变换。** 这就是"黑白没纹路"。
换 soft-light 也一样（实测纯白上仅 3.2% 可见度）。

同时它在中间调炸掉：overlay 在 base≈0.5 处斜率最大，实测中调归一化对比冲到 **340%**（参考图 18.5%）→ 这就是"烟熏感"。

### ★ 参考图的物理事实（实测 7 个色块）

| 区域 | 亮度 | 梯度 RMS | 绝对摆幅 |
|---|---|---|---|
| 白云 | 220 | 19.68 | 106 |
| 中蓝 | 196 | 18.84 | 129 |
| 深蓝海 | 100 | 10.42 | 159 |
| 白珠边 | 115 | 18.44 | 252 |
| 深紫 | 181 | 18.69 | 207 |
| 右下深蓝 | 70 | 7.04 | 53 |
| 左上浅蓝 | 173 | 18.58 | 132 |

→ **梯度 RMS 7~19.7、绝对摆幅 53~252，都与底色亮度无关。**
→ **真实浮雕的明暗是绝对量**：深色豆的纹路不是"更深"，而是同样幅度在深色区间起伏。

### ★ 解法：像素级绝对光影合成（替代混合模式）

```
out = base + L × SWING      （L ∈ [-1,1] 是光影场，SWING 是摆幅）
```
摆幅恒定 = SWING×2，与 base 无关 —— 天然满足参考图物理事实。

**软压缩 knee**：超界不能硬 clamp（会把黑白端纹理切平，正好是要修的问题），按比例压缩溢出部分。

### 走过的三条死路（都验证过，别再走）
1. **换 soft-light**：纯白仍只有 3.2%，无效
2. **multiply+screen 双向 + 自适应 alpha**：亮度偏移从 -90 收敛到 -26~+5 但仍不干净。根本原因是 `screen` 公式 `1-(1-a)(1-b)` 在亮底上提亮空间趋近 0，压暗却一直生效，**不对称没法靠 alpha 配平**
3. **绝对光影 tile + source-over**：摆幅恒定成功，但会整体压暗亮度（纯白 235→151），同样需要 alpha 配平，回到死路 2

### 最终改动（mixins/IronPreviewMixin.js）
- 新增 `_applyPixelRelief(ctx, w, h, cfg, swing, knee)` —— 像素级浮雕
- 新增 `_ironLightTile(cfg)` —— 脊线高度 → -1..1 → 存成 0..255（128 中性），带缓存
- 新增 `_ironSampleLightField(tile, w, h)` —— 平铺采样成 Float32Array，复用 scratch canvas
- 常量 `_IRON_RELIEF_SWING: 145`、`_IRON_RELIEF_KNEE: 0.45`
- 澡巾烫分支改为调 `_applyPixelRelief`，不再走 `_fillWithTilePattern`

**踩坑：`getImageData` 认设备坐标，不认当前 CTM。** 调用点已 `ctx.translate(padding,padding)`，
直接 `getImageData(0,0,w,h)` 会读到画布左上角透明区 → 浮雕错位。必须用 `ctx.getTransform()` 反解原点。

### 验证结果（决定性）
同一张图（纯白/纯黑/中蓝/浅蓝/深蓝五色块），新旧方案梯度 RMS 对比：

| 色块 | 新方案 | 旧 overlay |
|---|---|---|
| 纯白 | **8.2** ✓ | 3.2 ✗ |
| 纯黑 | **5.5** ✓ | 2.0 ✗ |
| 中蓝 | **9.3** ✓ | 13.0（过强）|
| 浅蓝 | **9.4** ✓ | — |
| 深蓝 | **7.1** ✓ | — |

**均衡度 6.5× → 1.7×**（参考图 7~19.7 区间）。摆幅 97~163 落在参考图 53~252 内。
性能：250 sparse 4078ms（优化前 10205ms，无退化）。

### ⚠ 尚未解决：纹理形态不对
算法（黑白显纹）已解决，但**形态仍是"大理石/水波纹"，不是"老虎皮毛细密短毛"**。
原因：`warp` 把低频 ridged 脊线揉成了涡卷。
- warp=0 → 各向异性 223（过度规整的平行线）
- warp=0.22（当前）→ 22（大理石涡卷）
- 参考图要 3.7~7.4

已测出 `fy=32` 时脊距 11px = 每颗豆 2.7 条脊，密度对了，但形态仍被 warp 揉碎。

**下一步方向**（未实施）：参考图的"细密短毛"很可能来自**高频 fbm 取绝对值**，
而不是现在的低频 ridged 噪声。需要换形态生成方式，而不是继续调参。

## 第五轮：修 file:// 协议下的画布污染（hh 真机报错）

### hh 的报错
```
Uncaught SecurityError: Failed to execute 'getImageData' on
'CanvasRenderingContext2D': The canvas has been tainted by cross-origin data.
  at handleCustomEditMouseDown → chainRazor
```
截图尺寸 504x444，走的是双击 `index.html`（`file://` 协议）。

### ★ 根因：`URL.createObjectURL(file)` 在 file:// 下必然污染画布

原来 `ImageCropMixin.loadImage` 用：
```js
const objectURL = URL.createObjectURL(file);
img.src = objectURL;          // blob: URL
```
`file://` 页面的 origin 是**不透明来源(opaque origin)**，而 blob: URL 继承创建者 origin →
两者不匹配 → canvas 判定 tainted → 之后**全站所有 getImageData / toDataURL 都被拒**。

承重范围：`PixelArtMixin.js` 两处（`drawOriginalImage` + `updatePixelatedImage`），
而它是像素化 / 颜色统计 / 画笔 / 剃刀 / 雕刻的数据源 —— 一崩就是整个编辑器不能用。

注意：报错位置在 `chainRazor`，但**跟我这几天的改动无关**，是原有的上传路径问题。

### 修法（两道）

**第一道（根治）**：`ImageCropMixin.loadImage` 改用 `FileReader.readAsDataURL`
—— dataURL 是纯字符串、不带来源信息，任何协议下都同源。
代价：多一次 base64 编码（20MB 图多占 ~1.3 倍内存、几十毫秒），换来 file:// 双击能完整跑通。

**第二道（兜底）**：`PixelArtMixin` 新增 `_safeGetImageData(ctx, w, h)`，
捕获 SecurityError 后 `console.warn` 提示（"若在用 file:// 协议打开，请改用本地服务器"），
返回 null 而不是让异常冒泡。像素化入口判空后提前返回。
—— 万一以后还有别的路径污染画布，至少"能看图能导出，只是不能编辑"，而不是整页崩。

### 其他 createObjectURL 调用都是安全的
`BrushPanel.js` / `app.js` / `FileIOMixin.js` / `InfoPaperManager.js` 里的
createObjectURL 全是 **Blob 下载**（`link.href = url` 直接触发下载），
不涉及画布读像素，不污染。已逐个确认。

### 无法在本地复现（诚实说明）
- 无头 Chromium（SwiftShader）对 blob 比真 Chrome 宽松，**没复现污染**
- 真 Chrome headless 也没复现（headless 模式放宽了这个限制）
- 我的测试 JPEG 字节也有问题（`toDataURL` 失败），结论不可靠
- **所以这项修复必须由 hh 在真机（非 headless、双击打开）验证**

- 外部 PNG 文件已删除，避免混淆

### ★ 量化环节踩的坑（两次，都写进 tools/gen-iron-textures.py 注释了）
1. **双重力量化**：`dither_quantize` 里 `new = round(old/step)*step` 已经量化过一次，
   存回时又 `round(new/step)` 减了一次 → tile 只剩 0~16，均值 7.9。
   表现为"光影范围 -1.000~-0.875"，整块被压暗而不是浮雕。
2. **在"级数"空间减均值**：级数是 0~15，均值约 7.5，
   减完再 clip 到 [0,15] → 整体塌到低端（灰阶 8~120，均值 29）。
   **必须在最终灰阶（8..248）空间平移。**

最终做法（简单且对）：
```
gray = clip(round(light/16), 0, 15) * 16 + 8      # 量化到 16 级
gray = clip(gray + round((128 - gray.mean())/16)*16, 8, 248)   # 灰阶空间对齐中性
```
结果：灰阶 8~248，均值 120~136（16 级精度极限），量化噪声 std=4.6（摆幅 145 的 3%）。
光影范围 -0.94~0.95，摆幅 1.63 → 双向均衡，实拍质感保住了。

## 第七轮：熔融外翻边（Metaball / 平滑并集）

### 需求（hh 草图 + 提示词）
凹角处要像波浪一样连续过渡，不能是直角折断。
hh 提供了 SVG Gooey 滤镜方案（feGaussianBlur + feColorMatrix 压硬 alpha）。

### ★ 为什么不能用 SVG Gooey
1. **它对所有色块生效** → 内部色块也糊在一起，颜色全毁（实测"稀疏点阵"整片化开）
2. **`ctx.filter = 'url(#goo)'` Chrome 不支持**，必须走 DOM `<img>` + CSS filter
   → 要放弃 canvas 渲染管线，跟现有纹理/光照/像素浮融全部冲突
3. 即使只做局部，也会把内部格线一起盖掉

→ 改为在 Canvas 里手写等价的 metaball。

### 效果名称（hh 问的）
- 工艺名：**熔融外翻边**（melted flare edge / sintering flare）
- 数学名：**变半径平滑并集**（variable-radius smooth union）
- 核心区别：半径不是常数，沿轮廓起伏；平滑并集 smin 替代硬并集 min

### 实现（mixins/IronPreviewMixin.js）
- `_buildMetaballMask()` —— 格子分辨率 SDF → 双线性插值到全分辨率 → 阈值成 mask
- `_ironCellDist()` —— 圆角矩形 SDF（iq 的 sdRoundBox），内外都正确
- `_ironSmin2(a,b,k,span)` —— 平滑并集，**带融合范围上限**
- `_ironMaskToPath()` —— marching squares 从 mask 提轮廓 Path2D，供 clip()
- `_ironGeometryCached(..., melt)` —— melt=1 时走 metaball
- `_ironPieceLayer` 熔融分支：drawImage(mask) + clip(maskPath) + 后续层照旧
- UI 加「熔融边」复选框（默认关）

### ★★ 最重要的性能发现：格子分辨率 SDF
逐像素算 SDF = 每像素 9 次距离，**2800×2800 实测 1824ms（不可接受）**。
但 SDF 本身平滑，相邻像素差 < 1px → **在格子中心算（每格 1 点），再双线性插值**。
实测 **1824ms → 5ms（360×），轮廓零差异**。

（先试过"每豆只写周围 r 范围"的增量法，无效 0.9~1.1×，
 因为 SDF 计算被 9 次 distToCell 主导，豆子密度高时跳空格判断几乎不生效。）

### ★★ smin 必须加 span 上限（最关键的坑）
教科书写法 `smin(a,b) = min - h²·k/4，h = max(0, k-|a-b|)/k`，
**在 |a-b| 很小时也会无条件收缩**，不管两点是否真的贴在一起。

实测后果（checker 图案：豆子只斜对角相接）：
```
空隙格心到四个豆距离全相等 → smin 无条件收缩 k/4
→ k=2 时空隙格心距离变 0.0 < bias → 全被判成品
→ 整个图案糊成一片条纹
```
解法：`_ironSmin2(a,b,k,span)` —— 距离超过 span 的走纯 min，完全不影响形状。
`span=0.35` 格（明显小于豆间空隙 1 格）。

### ★ 参数：R 和 K 都得小（demo 的 r=40px 不能照搬）
demo 里豆径 18px、r=40px → **r > 豆径，把整个方块吃成圆形**。
必须按比例：R = 豆径 × 0.18。
K 也得小：smin 最多拉低 k/4，K 大了会把空隙也拉成成品。

最终值：R=0.18, K=2.0, BIAS=0.02, SPAN=0.35

### 验证
- 九模式 × 熔融开关 = 18 组全部 PASS（非熔融路径无回归）
- 缓存 key 含 melt，切换后第二次命中缓存（3ms）
- 大图 100×100：熔融 469ms（非熔融 593ms，还更快）
- SDF 矩阵逐格验证：实心豆 -0.50（内部）、凹角格 +0.50（外部）判定准确
- 修了两个真 bug：`_drawIronShadow` 用了 null 的 geo.path；`_applyRimHighlight` 同理
  → 都改成 `geo.maskPath || geo.path` / `geo.outline || geo.maskPath`

### 未完成（诚实说明）

  但满屏斜对角时相邻豆本来就贴在一起，会连成片。
  判断：真实拼豆图案不会有这种结构（实测 mixed/photo 型是正常的）。
  **需要 hh 用真实图案验证。**
- 最终视觉没能在浏览器里确认（我的测试页 HTML 替换多次没生效，截图一直是旧的）。

### ★★★ 但发现熔融边实际是 no-op（严重）
做验证时发现四个参数里 **r 和 k 完全不影响输出**，只有 bias/span 生效。

**根因：`_ironSmin2` 的 span 守卫把所有 smin 都短路了。**
```
内部格的第二近邻居恒在 0.5 格 > span=0.35
→ 走纯 min → smin 从未生效
```
所以上一轮标定的 `span=0.35` 等于把功能关掉了。真机勾上熔融边大概率看不出区别。

### ★★ 更根本：span/k 从原理上无法区分凹角与空隙（重要教训）
实测数值（mixed 斜纹凹角 vs checker 满屏斜对角）：

| | 凹角 | checker 空隙 |
|---|---|---|
| 格子级 SDF | **+0.5** | **+0.5** |

**完全相同。** 两豆斜对角相接的几何在两种情形下一模一样，距离域里没有任何特征能区分。
span 扫描的临界点精确落在 0.5（凹角 d≈0.527 vs 空隙 d=0.5，只差 0.027 格）：
- span ≤ 0.35 → smin 全短路（无融合）
- span ≥ 0.50 → 全糊（100% 覆盖）

**没有中间可用区间。** 试过「连通域白名单」（flood fill 找被包围的小空腔）也失败 ——
因为判定在 smin 之后已经全通过，白名单根本没机会介入（hole=0 时也是 100%）。

**结论：metaball/距离域这条路上，凹角填充必须换判据，不能靠距离阈值。**

### 可行的替代判据（下一轮方向，未实现）
1. **拓扑判据**：空腔是否「被豆子包围」—— flood fill 透明格连通域，
   不连到画布外沿且面积小 → 是凹角（该填）；连到外沿 → 是外部（不该填）。
   ★ 必须在**不做 smin**的原始 SDF 上跑，且填的是「该空腔内的像素」而非改 SDF
2. **半边填充**：只填到空腔面积的 ~60%，形成弧形而非实心（更接近熔融观感）
3. **接受现状**：凹角不改，只保留豆子自身的圆角（r 单独用，k/span 删掉）

### ★ 关键差异：矢量图 ≠ 实拍照片
量化对比：
| | 实拍澡巾 | 矢量花纹 |

### ★★★ 无缝化：只有「边界淡出」这一条路成立
试了 4 种，前 3 种全废：

| 方法 | 结果 |
|---|---|
| 四象限镜像 + 环形对齐（照片那套）| **正中留明显十字接缝**（矢量花纹旋转 90° 不连续，照片织纹各向同性才看不出）|

## 第十轮：修复「点预览无反应」（弹窗崩溃）

### 症状
hh 点「✨ 预览成品效果」无反应，控制台：
`Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')`

### 根因：三个叠在一起的 bug

**① texPanel 整块代码被后续 patch 覆盖掉了**
上一轮我用多次 `python replace` 插面板构建代码，其中一次替换的锚点
`// ---- 熔融参数面板（默认收起）----` 被自己插入的代码覆盖，
导致 `const texPanel = ...` / `const texResetBtn = ...` **从未被执行**。

**② 用 querySelector 查 JS 动态创建的元素 → 必然 null**
```js
const texResetBtn = controls.querySelector('#ironTexResetBtn');  // null！
```
这两个按钮是 `document.createElement` 出来的，
在 `controls.appendChild(texPanel)` **之前** querySelector 必然返回 null。
→ 改成**直接用创建时的变量引用**。

**③ texPanel 从没被 appendChild**
`modal.appendChild(controls); controls.appendChild(meltPanel);` —— 只有 meltPanel。

**④ meltResetBtn 声明被误删**
删 querySelector 那行时连带删了 `const meltResetBtn = ...` 的声明，
但 450 行还在用它 → 引用了别的作用域的同名变量（语法检查通过，运行时才炸）。

### ★★★ 教训（比 bug 本身更重要）

**A. 语法检查通过 ≠ 能跑。**
`node -e "new Function(...)"` 只查语法，查不出：
- 变量作用域错位（声明被删，引用还在）
- querySelector 返回 null
- DOM 元素从未被创建

**B. 改完必须构建 + 在真实页面上点一遍。**
我上一轮交付时只跑了 `new Function(...)` + 无头测试页（测试页自己建了干净的 DOM），
**从没用真实 index.html 点过这个按钮** —— 所以这个崩溃本该在交付前抓到。

**C. 定位这类崩溃最快的办法：读 bundle 里出错行的上下文。**
```bash
node -e "const s=require('fs').readFileSync('js/bundle.xxx.min.js','utf8');
         const L=s.split('\n')[840]; console.log(L.slice(col-420,col+120))"
```

## 第十一轮：织纹素材编辑器（texture-editor.html）

### hh 的需求
「可以做一个素材编辑器吗，就是可以导入素材然后编辑的，然后可以原地保存或者新导出」——
原因：tile 存成 base64 内联在 tiles.js 里，没法直接看/改，想手动微调。

### 设计判断（概念先行的部分）
tile 是**量化过的浮雕数据**（128=中性），不是普通图片 →
在图片编辑器里涂它没有意义。真正的旋钮是**生成参数**：
无缝化策略 / 高通半径 / 高斯模糊 / 淡出宽度 / 裁哪一块（=花纹大小）。
所以做成「调参 → 预览 → 导出」，而不是像素画笔。

### 交付
`texture-editor.html`（36KB，纯前端，双击即开，不进 build.js）
- 导入：按钮 / 拖拽，多选
- 参数：裁剪·旋转·翻转 | 策略(自动/淡出/镜像)·高通·浮雕化·淡出 | 幅度·量化
- 预览：2×2 铺贴（看接缝）+ 单张放大 + 处理前原图
- 实时指标：接缝跳变 LR/UD、灰阶均值（应≈128）、std、耗时
- 导出：单张 PNG / 全部 PNG + 完整 tiles.js（可直接粘回 data/iron-textures/）
- **全部在浏览器本地跑，不上传**

### ★★ 算法移植踩的坑（都是 numpy→JS 的经典陷阱）

**① np.cumsum(np.cumsum(ap, axis=0), axis=1) 的方向**
axis=0 是**纵轴**。我写成「先 x 后 y」→ 窗口和整体偏移，输出全错。
对拍方法：`a=arange(25).reshape(5,5)`，`boxBlur(r=1)[0][0]` 必须 = 4.0。
（这个基准值是 Python 跑出来的，直接当断言用。）

**② 边界模式：reflect ≠ clamp**
numpy `mode='reflect'` = **不重复边缘**（…2,1,0,1,2…）
clamp = **重复边缘**（…0,0,0,1,2…）
用 clamp 会让均值偏大、左右边缘算错。

**③ 积分图数组长度要 +1**
窗口右边界 x+k 最大到 EW，若数组只开 EW 长度 → 越界。
（第一版写了 `new Array(EW)` 直接崩。）

**④ quantize 的 shift 公式抄错了**
我写 `Math.round((128 + TILE*TILE/2 - mean)/LS)*LS` —— 那个 `TILE*TILE/2` 是垃圾项，
导致输出恒为 247（纯白）。正确：`Math.round((128 - mean)/LS)*LS`。

**⑤ fillRect 的三重钳制**
- 采样坐标要钳在图内（否则 getImageData 之后 undefined）
- sw/sh 要钳在 tile 尺寸内（crop<1 时 sh 可能远超 TILE → A[y] undefined）

### ★ 接缝指标要加下限保护
`接缝跳变 / 内部梯度`，分母趋近 0 时算出 **3e10** 这种爆表值
（纯色/极低对比 tile 内部梯度=0）。加 FLOOR=1.0 灰阶，
低于它就报「内部几乎无纹理」并提示调大浮雕化。

### 对拍结果（JS vs Python，同参数）
| 素材 | 接缝 | 均值 | std |
|---|---|---|---|
| zaoJin3 | 1/0.89 vs 0.89/0.79 ✓ | 135.6 vs 135.6 ✓ | 55.3 vs 53.2（1.04x）|
| huaWen3 | 0/0 vs 0/0 ✓ | 135.5 vs 135.6 ✓ | 53.3 vs 36.8（1.45x）|
| huaWen2 | 0/0 vs 0/0 ✓ | 135.8 vs 121.9（偏14）| 41.2 vs 65.8（0.63x）|

逐像素不一致（抽样差 100+）是**预期内**：
Python 用 PIL LANCZOS 降采样 + 真高斯；JS 用 canvas 最近邻 + 三次盒式近似。
**统计特征对齐即可** —— 编辑器的用途是看形状调参数，不是像素级复现。

## 第十二轮：★ 按花纹周期取单元（大块纹理）★★

### hh 的反馈（这次是真正的需求错位）
「有轨迹边界的素材，我们的纹理表达不好。我们这次是比较大的素材图片，纹理也比较大，
但你只选取了一部分，这样就缺少了美感，能不能做比较大块的纹理啊」

### ★★ 根因：我把整张 1076×884 压进 256 tile
| 素材 | 真实周期 | 压到 256 后 | 一颗豆=30px |
|---|---|---|---|
| 蓝白青海波 | **311×320** | **42px** | 比一颗豆还小 → 每颗豆只有半截花纹 |
| 棕白鱼鳞 | 190×392 | 28~98px | 碎片 |
| 红白 S 波 | 132×132 | 36px | 碎片 |
| 黑白斜线 | 221×63 | 20px | 碎片 |

**这就是「缺少美感」的物理原因**：花纹被压到比豆子还小，形状全丢，只剩噪点。

### 解法：按真实周期裁一个完整单元 → 缩放 → 整数倍环绕
```
detect_period()  roll 验证法测周期
      ↓
unit_to_tile()   裁单元 → 按 density 缩放 → 整数倍环绕铺满 256
      ↓
unit_seamless_light()  高通 + 距离场化 + 边界淡出 + 中心区归一化
```
结果：青海波单元 128px（≈4.3 颗豆），S 波 128px，鱼鳞 128px，斜纹 32px。
**12 档（4 素材 × 3 密度）全部接缝 0.00/0.00。**

### ★ roll 验证法比自相关可靠（重要）
自相关给过 **3px 这种假周期**（噪声频段被误判成峰），完全不能用。
roll 法：把图按候选周期 roll 回去，周期对了差异最小。**全局验证，假阳性露馅。**

实测四张的「得分占基线比」：
| 素材 | x | y | 结论 |
|---|---|---|---|
| 黑白斜线 | 99% | 99% | **两轴都对不齐**（斜向条纹，roll 无解）→ 检测失败，手填 |
| 红白 S 波 | 23% | 21% | ✓ 真周期 132×132 |
| 棕白鱼鳞 | 96% | 57% | 部分（y 是 2 倍周期 392）|
| 蓝白青海波 | 81% | 92% | ✓ 真周期 308×308 |

**★ 两轴必须独立判定**：斜纹两轴都 99%，鱼鳞 x 对齐 y 不对齐。
阈值 0.95，单轴无效时借用另一轴，两轴都无效才返回 None。

### ★★ 缩放比不能用 max(px,py) —— 斜纹会被压碎
斜纹单元 221×63（长宽比 3.5:1），按长边算 → 缩到 64×18，**沿边 4×15 = 碎成渣**。
改用**几何平均** `sqrt(px*py)`：→ 128×32，单元 32px ≈ 1.1 颗豆，可用。

### ★★ 整除修正：np.ceil 环绕会多出一倍
单元 100px、tile 256 → `ceil(256/100)=3`，tile 里变成 3×3=9 个而不是 2×2=4。
必须把缩放后的单元尺寸**调到 256 的整数分之一**（1/1、1/2、1/3、1/4…）。

### ★ isVectorLike 阈值 0.15 太严（导致接缝爆表）
四张里有三张被判成「实拍」→ 走 mirror 分支（无淡出）→ 接缝 3~15。
两条修正：
1. 阈值放到 0.06
2. **有周期就直接判矢量** —— 有重复周期本身就是矢量花纹的定义

### ★ 归一化只能用「未淡出的中心区」（第二版也踩）
Python 版和 JS 版都踩了：全图统计会把边缘拉回有信号（边缘均值 146≠128），接缝又回来。
修好后：边缘均值 127.0，全图 127.4，首尾跳变 **0.00**。

- 新增「花纹密度（矢量纹）」分组：单元数滑杆(1~6) / 自动检周期开关 / 周期X / 周期Y
- 只在矢量素材上显示（vectorOnly）
